ACL2 on WebAssembly

ACL2 built on ECL compiled to WebAssembly, with the prover's own functions and certified books ahead-of-time compiled to wasm modules that ECL loads at run time.

Pages

  • ACL2 in the browser The theorem prover itself, at a prompt in about 9 seconds. It installs a serialized world image instead of running the boot strap, and passes ACL2's own check-acl2-initialization on the way. One session stays alive between submissions -- type a defun, then a defthm that uses it, then (include-book "textbook/chap11/qsort" :dir :system), then (perm (qsort (list 2 1 3)) (list 1 2 3)). A small tutorial set is shipped certified and compiled from ACL2's own expansion files: textbook/chap10/fact and textbook/chap11/{perm,perm-append,qsort,mergesort} (qsort and mergesort both define orderedp, so include one or the other). Loading a compiled book is the deepest recursion a page sees: these fit, and a book compiled from its source instead (most community books, e.g. projects/apply/top) needs more than the ~1 MB of engine stack a page gets and is refused with a message rather than hanging. Firefox gives a page about three times the stack.
  • Interactive ECL console A real REPL: one ECL instance stays alive between inputs, so definitions and values persist. Enter evaluates; arrow keys recall history.
  • ECL smoke test Instantiates the wasm ECL and evaluates a couple of forms. ~1 s.
  • Dynamic linking Loads a compiled Lisp module into the running ECL in the page and calls its functions. ~0.4 s.
  • ACL2 by boot strap The other route: loads ACL2 and lets initialize-acl2 run. It gets through the first pass and then stops, because the boot strap needs several megabytes of native stack and a page has about one. acl2-main.html is the one that works.

The page preloads the whole AOT tree, installs the serialized world image, passes ACL2's own check-acl2-initialization, and then takes one form at a time: ECL is entered through ecl_page_start, ecl_page_load and ecl_page_eval instead of main, so no read-eval-print loop runs and nothing exits between forms. Start to the prompt in a page: 8.9 s.

The remaining gap

Loading a big compiled module needs more stack than a page has. The depth is inside si::load-binary -- the engine's processing of a wasm module's constants, not the book's own events -- and it grows with the module. A Chrome page gives about 1 MB of engine stack: textbook/chap10/fact, std/portcullis and projects/apply/apply load; projects/apply/top needs 1.08 MB and does not. Nothing in a page can raise that limit, although Firefox's page stack is roughly three times Chrome's. A book that does not fit is refused with a message, and the session can be reloaded.

So the work ahead is to reduce that recursion — or to ship a base that does not boot-strap in the page at all. Details, measurements and the two bugs that made the AOT path work are in WASM-PORT-NOTES.md and wasm/web/README.md in the repository.
